# Findings

Static analysis only. No device has been connected and nothing from `vendor/` has been executed.
Inputs are pinned by SHA-256 in `vendor/SHA256SUMS` (regenerate with `scripts/fetch.sh`).
"Verified" means read directly out of a shipped binary. "Inferred" means it follows from strings or
names and still needs confirmation by decompilation or a real device dump.

## 1. Device transport: USB mass storage (verified)

The device does not use a custom USB protocol. `/usr/local/bin/gadget.sh` in the 14142 rootfs:

    modprobe g_file_storage file=/dev/hda1 removable=1 stall=0

`hddmount.sh` mounts the same partition on the device as `vfat` at `/mnt/public`. HDD layout from
`fdisk_hdd`: partition 2 is 500 MB (ext3, `/mnt/vf`, system) and partition 1 is the rest (FAT32,
type `c`, the user library). When docked, the host sees an ordinary FAT32 removable drive.

A replacement Editor therefore just reads and writes files on a mounted volume, so it works the
same way on Windows, Linux and macOS. `ether.sh` also has a `g_ether` mode (device at
192.168.17.17, from `/etc/paceIpAddr`), but nothing in the boot path calls it. Treat it as a dev
or debug path.

## 3. Database schema (verified)

`notes/schema-14142.sql` is generated by `scripts/gen-schema.py` straight from the `tl::g_*Fields`
symbol arrays in the unstripped `pmplayer`. It loads cleanly into SQLite. Tables: `tracks` (46
columns), `mixes` (17), `mixtracks` (8), `cases` (16), `casetracks` (2), `miximages` (2),
`trackmap` (5).

Indexes, verbatim from pmplayer:

    CREATE INDEX mixtracks_idx ON mixtracks (track_id)
    CREATE INDEX tracks_location_idx ON tracks (location)
    CREATE INDEX casetracks_idx ON casetracks (track_id)

The Editor additionally creates `index_bpm`, `index_genre`, `index_album`, `index_artist` and
`index_title` on the `ind_*` columns.

Column definitions are byte-identical across all seven firmwares (13557, 14108, 14142, 16219 and
the 2012/2014/2015 betas), and every one ships `EDITOR_COMPATIBLE_FLAG="002"`. There is one format
to target, not seven.

Compatibility hazards a replacement must handle:

- **Custom SQL functions and collation.** pmplayer registers `icuCollationTable` (loaded via
  `icu_load_collation`), `PreCollateTitle`, `GetFirstTitleUChar`, `GetDateFunc` and `GetKeyFunc`.
  Queries use `COLLATE icuCollationTable`. Stock sqlite3 can read the tables, but anything that
  touches an index or view defined with that collation needs the collation registered.
- **Schema versioning.** The Editor migrates through `Convert from version 1 to version 2` …
  `11 to 12` with `PRAGMA user_version`. The current value is *inferred* to be 12 and is
  unverified. Check it against a real `music.db` before writing one.
- **Negative track_id convention.** Removing a track from the library rewrites references with
  `track_id = -track_id` and fills `dup_title/dup_artist/dup_album/dup_play_time_secs`, so mixes
  keep a placeholder for missing tracks. A writer has to preserve this.
- **`trackmap`** (`ext_db`, `ext_id`, `int_id`, `tag_hash`, `location_hash`) maps external
  libraries to internal ids. The Mac Editor references `itunes music library.xml`, so this is
  probably iTunes import mapping.

## 4. Analysis data (partly verified)

Beat and gain analysis is a boost-serialization class `TrackAnalysedData`. Field names, verbatim
from pmplayer 14142 at file offset 0x850344:

- `normalizeFactor` (float; `setNormalizeFactor(float)`)
- `beatStartOffset` (long; `setBeatStartOffset(long)`)
- `realBeatLocations` (std::string; `setRealBeatLocations(const std::string&)`)

It is serialized with `xml_oarchive` via `TrackAnalysedData::save(juce::String&)` /
`load(const juce::String&)`. The Editor-side analysis strings include `firstDownBeat`,
`beatsVector` and `markersPerBeat`.

**Unresolved:** where the serialized blob is stored (the `tracks.structured_ct` VARCHAR(511)
column, the `pmdb_tracks/` files, or `.PD*.DB`), and how `realBeatLocations` encodes beats inside
its string. This is the main open question. Decompile `TrackAnalysedData::save` and its callers in
pmplayer (symbols are present).

## 5. Firmware images and update path (verified / inferred)

- Each `dfw_<ver>.pfw` is a raw **ext2** image (superblock at offset 0) of the system partition:
  `bin/pmplayer` (the whole device app, ARM ELF, **not stripped**), codec plugins,
  `boot/{zImage,cramfs.little,redboot.bin,system.xml}`, fonts and symbols. `scripts/unpack-firmware.sh`
  extracts it with 7-Zip.
- The rootfs (`cramfs.little`) is LTIB, Linux 2.6.19.2, read-only cramfs. Init order is in
  `/etc/rc.d/rc.conf`, and `pm-setup` → `pwrLauncherApp` → `pwrApplication` starts the app.
- Flash is **A/B banked** (`swConfig`: kernel on mtd2/3, rootfs on mtd4/5). Bank, status and
  upgrade flags sit in `/dev/mtdblock1` (`swGetStatus`/`swSetStatus.sh`), and `swUpdatePost.sh`
  marks a bank good after a successful boot. This should make firmware experiments recoverable,
  but that is *inferred* until we read the RedBoot side.
- Editor-side update (inferred from Mac Editor strings): download the compressed firmware, copy
  `dfw_*.pfw` onto the device volume, unmount, and let the device apply it on reboot. The
  download URLs in `paceStartupData.xml` (`www.pacemaker.net/Default.aspx?documentID=158/159/172`)
  are dead. The exact copy destination is not pinned yet.

## 6. The Editor binaries

- **Windows** `pacemaker.exe` 2.0.2.14170: native x86 PE32, VS2005 CRT, JUCE. rea's managed lane
  confirms there is no CLI header, so ILSpy-style recovery is not possible. Shipped inside an
  old-format InstallShield wrapper, which `scripts/isx.py` unpacks statically.
- **macOS** `Pacemaker.app`: universal (fat) Mach-O with full C++ symbols (≈105k mangled names,
  e.g. `DeviceCommunication::getFirmwareVersion`,
  `Communication::downloadLatestFirmwareAndUpgrade`). **This is the better Editor target.**
- The Editor and pmplayer share code (`tl::Repo`, `TrackAnalysedData`, `MixDocument`, the
  `xponaut::audioengine` namespace), so symbols recovered on one side carry over to the other.

## 7. Tooling status

- `rea` 6.5.0 (`npm i -g rea-agents`) is installed. On this host it fails every target with ESTALE
  under the system Node 22.14. It needs Node ≥ 22.19 on Windows. `scripts/rea.sh` runs it under the
  portable Node in `tools/node` until the system Node is upgraded.
- rea's managed (.NET) and artifact lanes work here. **Its Windows Ghidra lane only accepts
  x86/x64 PE**, so it can take `pacemaker.exe` but not the ARM `pmplayer` or the Mach-O Editor.
  Those need rea on Linux (WSL) or Ghidra headless directly. Ghidra 12.1.x and JDK 21 are not
  installed. The only JDK on this machine is 17.
- rea's firmware lane (binwalk/unblob) is Linux-only. It hasn't been needed: the images are plain
  ext2 and cramfs, and 7-Zip reads both.
